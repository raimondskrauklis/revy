## P1 — Credit check + increment

| Severity | Area | Finding |
|:---|:---|:---|
| high | codebase gap | **`ForbiddenError` escapes `prepare_review_after_index`.** `review_pipeline.py:285` catches only `ConflictError` and `ServiceUnavailableError`. `ForbiddenError` from credit check in `create_review_run()` (findings §1.4) will propagate as an unhandled exception, causing the pipeline to crash instead of returning `fail_pipeline_check=True`. Findings §1.6 identifies this correctly. General plan P1 says "ForbiddenError catch in autostart pipeline" but the delivery requires `from app.core.exceptions import ForbiddenError` + a new `except ForbiddenError as exc` block in `review_pipeline.py`. |
| high | plan ↔ findings | Credit check placement in `create_review_run()` is **after** `ensure_revision_access()` but findings says the workspace is "already loaded indirectly" — it isn't. `ensure_revision_access()` (at `github_indexing.py:104-133`) joins across revisions/pull-requests/repositories but does NOT fetch `WorkspaceORM`. The workspace must be fetched explicitly. Findings §1.4 correctly calls this out ("add workspace fetch right after ensure_revision_access") and the code at `create_review_run:629-635` confirms there's no workspace fetch. Implementation must add `workspace = await session.get(WorkspaceORM, workspace_id)` + `if workspace is None: raise NotFoundError(...)`. |
| medium | plan scope | Stripe downgrade path: plan says "Stripe webhook sets limit on downgrade" in P1 but the plan also says "Scope out: any reset/refund/UPSERT logic." The downgrade (`customer.subscription.deleted`) currently calls `_update_workspace_plan()` which sets `workspace.plan = "free"` — but no code sets `review_run_limit = 25`. `_update_workspace_plan()` is the **wrong** place to do this because the same function is called for upgrade (`checkout.session.completed`) and downgrade. The credit mutation must happen in `apply_subscription_event()` (line 310-312 in `billing.py`) **after** `_update_workspace_plan()` returns, conditionally on the new plan being `"free"`. This isn't called out in P1 deliverables — just says "Stripe downgrade → review_run_limit = 25". |
| low | edge case | `SELECT ... WHERE completed_review_runs < review_run_limit` (findings §1.5) works for increment but there's a subtlety: for pro workspaces with `review_run_limit = NULL`, the WHERE clause `NULL < NULL` evaluates to NULL (falsy in SQL), so no rows are updated. This is correct and desired, but worth validating in tests. |

## P2 — Frontend counter display + trigger gate

| Severity | Area | Finding |
|:---|:---|:---|
| high | access control | **Dashboard `PlanSummaryWidget` vs billing endpoint.** The plan says "extend BillingStatus schema" and "frontend reads via `useBillingStatus()`". But `useBillingStatus()` in `frontend/src/features/settings/hooks.ts:199-204` is gated behind `canManageBilling` (requires `admin:users`). The user's own dashboard `PlanSummaryWidget` already shows plan info without this gate — it reads from `useAuth().user.workspace_plan` via the `me` endpoint. If credit fields go on the billing endpoint, every workspace member needs to see their own counter, not just admins. This means either: (a) move the credit query to `me` endpoint (no auth change needed, user is self), or (b) split credit fields into a separate unauthenticated-by-role endpoint, or (c) remove the `canManageBilling` gate on the credit portion. The findings (Q3/Option A) doesn't surface this access-control mismatch. |
| medium | plan scope | Plan says "extend BillingStatus schema + `/workspaces/{id}/billing` endpoint" but `BillingStatus` is in `backend/app/schemas/billing.py:7-9` with only `plan: str` and `stripe_enabled: bool`. Adding `completed_review_runs: int` and `review_run_limit: int | None` is straightforward but the plan doesn't specify whether `review_run_limit` should be nullable in the schema (NULL for pro = unlimited) or serialized as a sentinel like `-1`. |
| low | i18n | Plan says "no warning banners" but `PlanSummaryWidget` today shows only a static string. With real counter data, the widget needs a loading state (when fetching billing/credit data) — the current widget has no loading state. |

**Verified OK:**
- `ReviewTriggerBar:77,88` — `busy` gating is correct; adding credit check is straightforward
- `PlanSummaryWidget.tsx:19-20` — ready to swap static `t('dashboard.planSummary.free')` for dynamic `{completed}/{limit} reviews used`
- i18n keys in findings §2.4 are comprehensive (EN+LV parity)

## Open questions (max 3)

1. **Dashboard credit visibility for non-admins:** Should credit counter appear on all users' dashboards (via `me` endpoint or un-gated billing) or only for workspace admins? If only admins, regular users won't see their own credit consumption. Which path?

2. **Plan downgrade credit behavior:** If a pro workspace downgrades and already has >25 completed runs, the immediate cap means `completed_review_runs=939 > review_run_limit=25` — the check `>= limit` fires instantly. Should the downgrade UI warn users, or is this intentional "instant consequences" as findings §6 states?

3. **Failed run UX:** When a user hits the credit limit, the API returns `ForbiddenError(credit_limit_reached)` — but what about the UI for the user who already triggered a review run that's `pending`/`processing` when the limit is hit? Those runs already passed the creation gate and will complete normally. Is this acceptable (credit check is a creation-time gate, not a completion-time gate), or should we also check at completion time?
