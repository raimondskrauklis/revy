P1 Missing created_at index for O8 retention purge

The execution contract (O8) explicitly ships a Celery beat task that will DELETE FROM github_pipeline_runs WHERE created_at < $cutoff. Without a created_at index on this table, that query is a full sequential scan on every scheduled purge run — a pattern that becomes increasingly expensive as pipeline data accumulates. The three existing indexes cover workspace_id and revision_id lookups, but the time-based cleanup path has no index to land on. This should be added here alongside the existing create_index calls:

op.create_index("ix_github_pipeline_runs_created_at", "github_pipeline_runs", ["created_at"])
The corresponding drop_index call should also be added to downgrade().

P1 Nullable FKs default to RESTRICT, blocking deletion of referenced records

index_job_id, review_run_id, and publish_job_id are all nullable — semantically they are optional links. However, the ForeignKeyConstraint declarations for all three omit ondelete, which means Postgres uses RESTRICT by default. Any attempt to delete a row from github_index_jobs, github_review_runs, or github_publish_jobs that has a referencing github_pipeline_runs row will be blocked with a FK violation. Because these FKs are nullable, the expected behavior on parent deletion is SET NULL. The same mismatch exists in the GitHubPipelineRunORM model's ForeignKey() declarations.

P2 Existing github_index_jobs rows backfilled as index_mode='diff'

Postgres immediately backfills server_default values to all existing rows when a NOT NULL column is added via ALTER TABLE. All previously completed jobs were full-repo tarball indexes, so they will be stamped index_mode='diff' — the wrong value. If any query later filters or reports on index_mode for historical jobs (e.g., audit, metrics, or a future pipeline read API), the data will be misleading. Consider backfilling with 'full' to reflect reality, or accepting the inaccuracy and documenting it alongside the D10-M decision.
